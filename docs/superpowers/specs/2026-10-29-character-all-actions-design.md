# 当前成年固定配方：全动作统一交付设计

日期：2026-10-29。状态：设计提案，尚未实施。用户已明确本轮以全动作统一交付为目标；本次请求交付设计执行方案。此前西walk单独阶段计划的任务边界由本设计替代，旧来源诊断继续作为证据使用。

## 1. 交付目标与范围

在同一制作合同、严格构建入口、Godot消费者和权威动作时间轴下，交付一个完整的成年固定衣装动作包：

| 维度 | 固定内容 |
|---|---|
| 体系/体型 | unified-composable-character-v1 / adult-standard-v1 |
| 动作集 | review-motion-v1；新增内容修订有独立SHA，不改写历史pose身份 |
| 衣装 | top03海军条纹上衣、original-pants原橄榄裤、original-shoes原棕鞋 |
| 头部 | 仅hair_hat：栗色短发hair-chestnut-short-v1＋藏蓝缎带草帽hat-straw-navy-band-v1 |
| 动作 | idle、walk、run、hoe、water、harvest |
| 方向 | south、west、east、north |
| 最终范围 | 24个动作方向单元×1固定发帽组合=24个能力单元，全部实际构建、加载、动态及原生验收 |

按当前模板数据，四idle加20个四pose动作共有84姿态，固定hair_hat组合对应84个姿态结果。此数是当前核查基数，不是锁死帧数的质量指标；必要增帧必须有来源、时序和重验证。PNG去重不减少能力覆盖要求。

统一交付物是**完整同配方评审动作包和可运行原生验收入口**。本轮不扩大到第二套衣装、8种动态混搭、其他体型或全体NPC，不建设自由衣柜。完整动作包不等于完整人体体系生产发布：正式游戏仍用player-unified-v4，生产统一替换、旧模型退出与导出另按唯一制作规范的发布门禁执行。

新交付不包含bare、hair-only或hat-only，也不要求为其他三种状态补全动作。已有四状态西锄成果与历史合同保留；需要的兼容回归不计入新增交付范围。

## 2. 方案选择

| 方案 | 收益 | 问题 | 结论 |
|---|---|---|---|
| 通用合同先行，按动作族补齐，最终整包验收 | 共用构建/加载/时间轴，逐批发现真实缺口，最后得到完整角色 | 初期需处理版本和登记 | 采用 |
| 每个动作方向单独做完整小样并分别交付 | 每次范围小 | 重复搭评审与验收，完整角色目标被切碎 | 不采用；内部检查可分批，但不是独立最终交付 |
| 直接拼合各旧样例批量输出 | 最快出现24个播放按钮 | 父衣装、款式身份、头部和源层不同，缺能力被数量掩盖 | 不采用 |

西锄已有小样保留，西walk只用于验证多target映射、循环移动和idle衔接，属于统一方案中的实现顺序，不另设“完成西walk即结束”出口。

## 3. 已有成果与真正缺口

[覆盖审计](../../reviews/character-first-recipe-coverage-audit.md)登记时，同配方衣装24格为2完整、3局部、19未登记；后来已交付西锄四状态严格构建与原生证据，[西walk准备](../../reviews/2026-10-29-walk-west-readiness.md)仅增加有限来源桥接与诊断。

- 旧locomotion/run及农事24参考可供核源；完整穿衣参考不是隐藏身体，也不是同配方已兼容。
- 四向top03静态完整源可复用设计身份；不能把站姿衣片直接平移到弯腰/摆臂帧。
- 西walk原下身与西锄idle的像素祖先桥接不能自动覆盖其他方向/动作。original-*旧标签需逐适配声明真实来源及有限兼容范围。
- 东跑、南浇、北收发帽是其他父衣装的线索；每次复用先核头部实际投影、源view、完整层、目标锚点与遮挡，不复制整套父身体。
- 需要补的内容可能是登记、层/映射接口、隐藏区或新绘制视图；执行前逐格分类，不能把“未登记”全部算成缺图，也不能一律假定已有像素足够。

## 4. 同一合同与数据流

数据流保持：完整GPT源及prompt → 来源/整帧注册 → 体型动作pose与部件views/适配 → 固定衣装基础配方 → 一份固定hair_hat配方 → `build.py build/verify` → 整包评审清单 → 同一Godot消费者/时间轴 → 原生证据。

扩展仍使用`coastal-character-construction-v1`，不写每批次合成脚本。提出schema3承载新增显式适配引用、source/target映射及层语义；schema1/2继续按原合同严格解释，不能借schema3改变旧配方含义。schema2头部组合需要允许已验证schema3基础配方；禁止多级任意嵌套。

新配方按明确file/SHA引用`parts/<design-id>/revisions/r002/design.json`及`adaptations/.../r002/views.json`，保留design_id，区分设计修订、适配修订和view。旧`design.json`、r001、已交付西idle输入不就地改写。路径规则由合同及测试显式扩展，未经支持不能先放文件绕过校验。

每个映射逐项绑定source_view_pose、target_pose、完整view、source ownership及其坐标、目标锚/pivot、合法整数放置、实际来源SHA。source仍是idle时不能改写成walk。coverage绑定具体目标表面，occlusion以有序子层优先；无需要时明确声明不用mask，不为满足旧三mask字段复制空白/同一张图。二值RGBA替换与alpha合成分别声明，避免透明边重复叠加。

全包采用一份固定hair_hat配方，引用一份全动作基础配方，包含24个clip。整包评审清单新增`schema_version:2`，按`samples`列出20个动作方向条目并引用一个hair_hat全包manifest，四向idle作为唯一canonical clips绑定；原hoe-west suite schema1保持其原有边界。消费者从clip数据读取pose数、时长、画布、根点、比例、事件及倍率，不硬编码四pose/西锄。

当前统一入口的函数签名`construct(repo, recipe, output)`、`verify(repo, directory)`及加载入口`load_samples(project, path)`保持；扩展其接受的明确版本数据。`review.py`增加`all-actions-construction` suite名称，实际运行现有评审场景的全包模式，场景提供动作/方向控件，头部固定为hair_hat，不提供换头状态控件。UI固定布局放.tscn，复用已有美术，新增正式美术才使用GPT。

## 5. 历史构建与当前依赖

构建器任何变化都会使当前四个strict build的engine身份过期。解决方式是**按新引擎重建当前制品，历史制品按冻结Git版本恢复**；不新增忽略engine的verify模式，不放宽runtime-baseline。

实施前记录`2742c19`中四个旧manifest/输入/输出、工具及原生轻量回执的Git对象与SHA，以及外部/private/tmp证据的实际存在性。版本化恢复说明和清单保存在`art/characters/evidence/all-actions-v1/history.json`。旧完整GPU临时资料不假称已入Git；若其为必须留存输入，应在变更前保全必要内容并核SHA。

引擎变更后，使用旧配方在新目录重建西锄四state，逐RGBA验证20个结果不变，当前hoe评审引用迁到新manifest；新hair_hat全包构建独立生成。旧strict目录退出当前`builds/`前，证明Git能恢复原字节及旧工具环境、旧认可引用不悬空，记录新旧映射；必要的旧证据引用改为明确历史Git对象，不伪装成当前路径。九个冻结legacy构建及runtime-baseline保持不变。该迁移作为同一工作包完成，最终check.py须验证所有当前strict构建；期间旧build stale必须如实记录，不宣称门禁通过。

## 6. 动作状态、接触与衔接

每个角色只有一份权威action、direction、elapsed、playback_rate、action_instance_id，所有层及烘焙纹理从同一pose解析。复用并扩展现有trial动作状态；面板独立预览不能冒充世界角色已切换。

- idle/walk/run根据移动切换；walk↔run使用实测支撑相位映射，缺映射时经声明的稳定过渡，不能直接假定帧号相同。
- 移动中转向映射整套层；急停进入该方向canonical idle；其他动作的idle也引用同一纹理，禁止不同动作各自带一套不一致待机。
- 农事开始固定方向、锁移动、按声明事件接触、结束回idle；本轮无业务取消功能时明确不可取消，不伪造取消合同。重播生成新instance，完成只通知一次。
- 本轮角色头部始终为hair_hat，不新增换装请求、切换控件或换装验收；头发与帽子作为可追溯部件分别保存，帽下发、近远帽层仍按每个pose验证。
- 事件用instance/event/loop身份按越过的时间区间去重，测试低帧率、暂停恢复和变速。隔离评审事件只记录，不扣物品/收获或写真实存档。

为固定配方登记实际足/握点、支撑/腾空、工具目标、根点及世界速度；实际屏幕误差目标≤1像素，按唯一制作规范执行。头部投影残差不能代替脚接触误差；不以整帧挪移、缩鞋、拉长工具或逐帧擦身体修视觉问题。无法满足的pose标rework_required，回到具体源/接口修复。

门槛是所有范围技术完成，视觉待用户认可时据实标记，不能提前宣布“全部认可”。Windows/Intel、物理键鼠/WM焦点及导出不由自动原生采集推导。全包技术交付不以这些未请求平台项为阻塞，但须列出未验证范围。

## 8. 分批执行与停止规则

顺序为来源矩阵及历史保全 → 一次性补统一合同/消费者 → 四向idle和walk → 四向run → 四向hoe/water/harvest → 全包构建、衔接和接触 → 原生整包验收。开发批次内部随时做相关验证，不到最后才第一次看画面；西walk通过后直接继续同一计划。

如某一pose必须补画，精确记录源、姿态、缺失表面与所需GPT产物，先处理其余独立动作；同思路失败两次先分析新证据。缺资源不能被统计为完成，也不临时换成另一套衣装。任务最终完成必须24格齐全；确有外部阻塞则明确未完成格和原因，不把局部结果改名全动作交付。
