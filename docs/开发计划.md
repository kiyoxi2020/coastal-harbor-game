# 《潮港旧屋》整体开发方案与进度

更新时间：2026-10-16。策划依据：[GDD v1.0](../潮港旧屋_游戏设计文档_GDD_v1.0.md)。

本文件是后续开发进度的唯一总表；GDD 负责愿景与玩法，阶段方案负责当阶段实现细节，PROJECT_STATE 负责当前工程事实，HANDOFF 负责下一步续接。当前已有P01–P14设计基线1，未开始新玩法编码，不代表完整产品承诺。执行入口见[设计任务包](design/p01-p14/README.md)与[共享合同](design/p01-p14/共享合同.md)。

## 1. 目标与制作路线

先完成可连续游玩 7 日的个人生活循环，再打通“种植／赶海 → 加工供货 → 餐馆自主营业 → 岗位与家庭迁入 → 世界可见变化”。先验证小规模闭环，再扩充四季、地图和商品。

选择：纵向切片，保留 Godot 4.7.1 / GDScript / Compatibility、现有操作与像素风。

| 可选路线 | 优点 | 代价与取舍 |
|---|---|---|
| 纵向切片（推荐） | 每阶段可试玩，尽早验证复兴特色 | 限制作物、店铺与人口规模 |
| 先铺完整模拟底层 | 规则容易集中推演 | 可玩成果慢，容易为未验证需求过度建设 |
| 先扩内容再接经济 | 短期内容丰富 | 后续库存、存档和经营可能返工 |

近期不做：全量城镇地图、实时大规模 AI、多人、复杂金融、完整恋爱、生育死亡。旅游民宿、钓鱼、装饰扩展与四季故事归内容阶段，不插入首个闭环。

## 4. 系统边界与数据流

静态定义 → 单一运行状态 → 规则/事务 → 事件与报告 → 场景表现。场景卸载不停止经营，不从NPC动画或UI文本反向推导生产状态。

| 模块 | 责任与数据 | 依赖 / 接入 |
|---|---|---|
| 商品与容器 | 稳定item_id、堆叠、来源用途；数量校验与转移 | 扩展既有scripts/inventory，不新建平行库存 |
| 钱包与交易 | 双方余额、库存/容量预检、全成或全败、event_id去重 | M0接库存；M1用于种子买卖；M2用于企业 |
| 游戏日与日结 | day_id、last_settled_day、按顺序计算候选状态 | M1接农田/刷新；后续逐段接企业、贸易与人口 |
| 农田与潮汐 | plot_id、作物、增长天数、浇水；资源点当日状态 | 表现放.tscn；规则不依赖画面节点存活 |
| 配方与企业 | recipe_id、投入/产出、企业钱包库存、工资与经营状态 | M2；玩家、店铺与居民资金分离 |
| 家庭与人口 | household_id、成员、预算、住宅与岗位唯一占用 | M2先消费模型，M3迁入与就业，不另建第二套家庭计数 |
| NPC与发展 | 身份、条件台词、日程；建筑状态和社区项目 | M3读取企业/家庭状态，按现有场景组织增量接入 |
| 区域贸易 | route_id、voyage_id、预算/运力/保留量、出发到达状态 | M4；明确外部物资和资金来源 |
| 存档与事件 | 版本迁移、合法性、快照与恢复、近期变动原因 | 延用version字段，避免另起save_version双版本源 |

不预建所有目录或Autoload，不大规模拆harbor.gd。新职责需要独立单元时才创建脚本，入口只负责装配与交互路由。新增静态节点、固定UI与布局放.tscn，配置优先Inspector或资源。

日结约束：先复制当前状态计算候选结果，按GDD §11.2顺序处理；验证后保存成功再发布新状态。写盘失败保留旧状态并允许重试；day_id与完成标记一起持久化。先验证本地单机完整快照方案，不直接建设通用分布式事务或全量事件溯源系统。日志用于解释与测试复现，不能把缺少初始快照的日志宣称为完整可重放历史。

## 6. 首轮原型建议值与决策时点

以下为方案默认值，未经试玩不写成最终策划。

- M1手动睡眠推进日期，不引入现实倒计时、强制倒下或离线收益；7日是一轮验收，不是整个季节长度。
- 生菜2个有效浇水日、番茄4个有效浇水日；未浇水暂停增长、不枯死；收获后需再播种。P01定值为初始100G、两种种子5/8G、每株产3个，见共享合同；属于首轮测试基线。
- 沿用三海产六点，每日最多拾取一次；先保证每日可用窗口。动态潮汐在M1基础通过后设计小任务，首版只改变点位可采状态，不改变通行碰撞，保留错过后的替代收入。
- 不引入体力耗尽、腐败和强制季节枯死。天气与季节字段仅在真正接玩法时增加，跨季测试随该系统落地。
- M2固定基础价和有限购买预算优先；供需浮价延后到固定价经济稳定。海带肥料必须处理，不能无限叠加；两个菜谱从现有海产和两种作物组合，不要求先实现捕鱼。
- M3约20人、首次1户3人为测试规模，NPC姓名尚未锁定。数值增长不能代替真实的家庭、住所、岗位和消费变化。

## 7. 验证与阶段闸门

每个逻辑任务：先写验收用例并观察失败 → 最小实现 → 定点测试 → 相关回归 → 原生交互/画面验收（涉及表现时）→ 更新进度。文档任务只做内容、链接与diff检查。

Godot命令模板（GODOT_BIN为实际已确认的引擎路径；占位名称在执行前替换，不直接复制运行）：

```sh
"$GODOT_BIN" --headless --path godot2d --log-file /private/tmp/coastal-<任务>-<测试>.log --script res://tests/<测试>.gd
```

测试脚本自身及完整场景的Save/Settings都必须隔离到/private/tmp/coastal-*；仅设置日志路径不足以隔离存档。全场景可使用已有--test-save-directory入口，使用前核对入口适用方式。逻辑检查不能替代可见交互；导出应用使用导出验证入口单独验证。

| 阶段 | 自动化证据 | 人工/原生证据 |
|---|---|---|
| M0 | 目录、容器、操作、存档及房屋存档定点回归 | 若未改表现，沿用基线；变化处补实测 |
| M1 | 交易失败原子性、一次日结、重载、作物与7日链路 | 菜畦各阶段、鱼摊UI、睡眠、室内外与日报 |
| M2 | 14日资金库存对账、工资/缺料/预算边界、场景卸载 | 餐馆复业、加工与断供恢复，玩家可解释变化 |
| M3 | 人口/住房/岗位唯一性、7日评估、加载幂等 | 3名NPC、住宅亮灯、20～30分钟切片 |
| M4–M7 | 30日贸易→100～365日长模拟、存档故障与性能 | 外部试玩、设置音画、目标平台导出应用 |

新增经济模拟需给初始资金/物资、外部输入和消耗事件分类，断言余额/库存非负、内部转账相抵、人口等于家庭成员总数。没有证据的功能记待验证，不记完成。

## 8. 进度维护规则

每次开始开发：读本表当前任务、PROJECT_STATE与HANDOFF，查git status，确定该任务完成条件及影响文件。一次仅推进一个任务，出现范围变化先修订任务卡。

每次结束（包括未完成）：

1. 更新上表对应ID的状态；进行中/阻塞写明剩余项、原因及下一步。
2. 在阶段记录中写修改文件、测试摘要和证据路径；临时路径注明可能被清理。
3. 本文件追加一条简短进展，写日期、任务ID、结果与下一项。
4. PROJECT_STATE同步已证实的新能力，HANDOFF同步唯一当前续接任务；不同文件不得维护不同完成状态。
5. 玩法或数值偏离GDD时，在此说明原因及影响；确认采用后再修订GDD对应段落。没有实际开发不勾完成，不在后台自动推进。

提交、推送、导出和发布遵循当次授权，不因计划中列出而自动执行。
